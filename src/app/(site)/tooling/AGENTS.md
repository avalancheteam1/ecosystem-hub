# Tooling

Rules for this area. The root `AGENTS.md` applies too.

## Tooling (`src/app/(site)/tooling/` - public `/tooling`, `/tooling/[slug]`, builders `/tooling/submit`, reviewers `/admin/tooling`)
- A public list of **builders' hub projects** in the "Developer Tooling" category, each reviewed by team1 before it is listed. Shown to users as **"Community Tools"** (no nav link of its own: reached via `/ecosystem` "Built on Avalanche", nav "Ecosystem", next to Cascade; copy says it's built by the community, not team1); the code, URL, table and permission keep `tooling`. Data: one `ToolingListing` row per project (`prisma/schema/tooling.prisma`); nothing is stored on the project itself.
- **Behind the `tooling` feature flag** (`/admin/flags`, default off, `paths: ['/tooling']`): while off, every URL under `/tooling` answers 404 for everyone (the proxy does it, no page checks), its card and preview on `/ecosystem` and its sitemap entries hide, and `submitToTooling` / `withdrawFromTooling` refuse (`requireFlag('tooling')`). `/admin/tooling` is gated by the permission only, so reviewers can approve projects before launch.
- **Only sealed versions are listed.** Submitting seals the project's current version (`SEAL_NOTE`, not `submissionNote()`: that prefix marks hackathon versions "replaced") and sets `pendingVersion`. A reviewer (`tooling.review`) approves it, which sets `approvedVersion` - the only thing `/tooling` shows. Edits never change the public page: they start a new draft, and the team resubmits (or a reviewer approves the newer sealed version directly, `newerVersion`). An approved version stays listed while an update waits.
- **Checks** (`listingProblems`, same on submit and approve): category "Developer Tooling", stage `live` or `established` (`LISTABLE_STAGES`), `missingForSubmission` empty. `approveProblem` adds: sealed, newer than the listed one, not older than the pending one, listing open, project not deleted.
- **Consent:** submitting requires `TOOLING_CONSENT` (checked server-side, `consent: true`); `consentAt` / `consentById` are stored with the submission and audited.
- **Public pages show project data only** - never the owner or team. `/tooling/[slug]` renders the approved version with `ProjectVersionView` and `hideCountry` (the country is where the team is based); the review page renders versions the same way, so reviewers see exactly what goes public. A deleted project (`Project.archivedAt`) disappears at once. A newer version with stage `archived` shows to reviewers as not approvable; they can remove the listing.
- **Lists page in the database:** `/tooling` (`listPublicTools`: `skip` / `take: PAGE_SIZE + 1`, search via `toolSearchWhere` on the approved version's name and short description, `approvedAt` then `id`; the `/ecosystem` preview uses `listPublicToolPreview`, same filter and order, `take` = the cards shown) and `/admin/tooling` (`listListingsForReview`: status filter, search on the current name, `updatedAt` then `id`; "To review" = a pending submission, a directly approvable newer version shows as "Newer" under All / Listed). The sitemap uses the slim `listPublicToolSlugs`.
- **Who does what:** owner / writer submit, withdraw and unlist (no reviewer needed; `withdrawPlan`). "Withdraw submission" takes only the version in review back: a listed version stays listed (nothing is recorded on the listing row; the project activity log has it, and a reviewer can still see and approve that sealed version as "Newer"), with nothing listed the listing closes as withdrawn. "Unlist" closes the listing (`closedReason: 'withdrawn'`, shown to reviewers as withdrawn by the team). Reviewers approve, reject (optional reason; `rejectReasonInternal` hides it from the team) and remove a **listed** version (`removeProblem`; a submission never listed is rejected instead; optional reason, `removedReasonInternal` hides it from the team, otherwise shown on `/tooling/submit`, `closedState`). A rejected or removed version can't be approved or resubmitted unchanged (`approveProblem`, `submitBlock`), also after a withdraw. "Removed" covers every version a reviewer could have seen on the review page (listed, pending, "newer"); a version the team creates or seals later, even one sealed in the moment of the removal, counts as changed, the same as a draft that existed at removal (the reviewer never saw it, and the team can submit it for review like any edit). Withdrawn / removed listings show nothing until the team submits again.
- **History stays on the row:** the last approval (`approvedAt` / `approvedById`), rejection (`rejected*`) and removal (`removed*`, `removedVersionId` = the newest of the listed, the pending and the project's newest sealed version as the server reads them, `removalBoundary`) are never cleared by a resubmit or another review action, so the next reviewer sees them on `/admin/tooling/[id]`. `currentRejection` says whether the kept rejection is still the latest event (what the team and the queue show). Those columns hold the latest of each. Every action also writes the project's activity log (`recordProjectActivity`, target = the listing, in the action's transaction): `submitted` (a version still waiting is `replaced`), `approved` (the listed one and an older waiting one `replaced`), `rejected` / `removed` (with reason and `reasonInternal`), `withdrawn` (the submission) and `unlisted`. The review page's **History** table shows these rows with names and UTC times; the team sees them per version on the project page.
- **Concurrency:** every review action sends the listing as the page saw it (`approvedVersionId`, `pendingVersionId`) and updates with that as the `where`; a second reviewer or a resubmit in between is refused ("reload the page"), never applied to another version. Submitting seals the current version inside the transaction and checks the sealed row. What keeps a concurrent project save from changing it afterwards is the save action's own `sealedAt: null` guard (`projects/_lib/actions.ts`: it starts a new draft when the version is sealed) - keep that guard. The save never touches `tooling_listings`, so the listing row lock doesn't protect against it.
- Every state change writes an audit entry on the listing (`ToolingListing`, `tooling.submit|withdraw|approve|reject|remove`). Review actions are idempotent on retry: if the listing already holds the requested result, they succeed instead of reporting a stale page. Because the rejection stays as history, a reject only counts as a retry while it is still the latest event on the listing the page saw (`isRejectRetry`); after an approval, resubmit or close it is stale.
- Submit locks the listing row (`SELECT … FOR UPDATE`, the row created empty if missing) before reading it, so a review in flight waits and is then refused by its `seen` guard; nothing is overwritten from a stale read. The lock only serialises tooling actions with each other.
- After saving, the project form returns to `/tooling/submit` (`?next=` on the "Edit project" and "New project" links, checked by `safeNext`).
- Foreign keys: the listing cascades with its project (like every child of `Project`); the version links are `NoAction`, so a single version can't be deleted under a listing.
- A version sealed by a tooling submission and later reused by a hackathon submission keeps `SEAL_NOTE`, so the project page never labels it "replaced". Harmless; noted so nobody "fixes" `wasReplaced` for it.
- Pure rules in `_lib/rules.ts`, tested in `tests/tooling.test.ts`. Later: public project pages, showing the team.
