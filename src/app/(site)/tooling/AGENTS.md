# Tooling

Rules for this area. The root `AGENTS.md` applies too.

## Tooling (`src/app/(site)/tooling/` - public `/tooling`, `/tooling/[slug]`, builders `/tooling/submit`, reviewers `/admin/tooling`)
- A public list of **builders' hub projects** in the "Developer Tooling" category, each reviewed by team1 before it is listed. Data: one `ToolingListing` row per project (`prisma/schema/tooling.prisma`); nothing is stored on the project itself.
- **Only sealed versions are listed.** Submitting seals the project's current version (`SEAL_NOTE`, not `submissionNote()`: that prefix marks hackathon versions "replaced") and sets `pendingVersion`. A reviewer (`tooling.review`) approves it, which sets `approvedVersion` - the only thing `/tooling` shows. Edits never change the public page: they start a new draft, and the team resubmits (or a reviewer approves the newer sealed version directly, `newerVersion`). An approved version stays listed while an update waits.
- **Checks** (`listingProblems`, same on submit and approve): category "Developer Tooling", stage `live` or `established` (`LISTABLE_STAGES`), `missingForSubmission` empty. `approveProblem` adds: sealed, newer than the listed one, not older than the pending one, listing open, project not deleted.
- **Consent:** submitting requires `TOOLING_CONSENT` (checked server-side, `consent: true`); `consentAt` / `consentById` are stored with the submission and audited.
- **Public pages show project data only** (name, logo, descriptions, links, repos) - never the owner or team. A deleted project (`Project.archivedAt`) disappears at once. A newer version with stage `archived` shows to reviewers as not approvable; they can remove the listing.
- **Who does what:** owner / writer submit and withdraw (no reviewer needed). Reviewers approve, reject (optional reason; `rejectReasonInternal` hides it from the team) and remove (reason required, stored as `closedNote` and shown to the team on `/tooling/submit`, `closedState`). A rejected version can't be approved or resubmitted unchanged (`approveProblem`, `submitBlock`). Withdrawn / removed listings show nothing until the team submits again.
- **Concurrency:** every review action sends the listing as the page saw it (`approvedVersionId`, `pendingVersionId`) and updates with that as the `where`; a second reviewer or a resubmit in between is refused ("reload the page"), never applied to another version. Submitting seals with a `sealedAt: null` guard inside the transaction and checks the sealed row, so a concurrent project save can't slip unchecked content in.
- Every state change writes an audit entry on the listing (`ToolingListing`, `tooling.submit|withdraw|approve|reject|remove`). Review actions are idempotent on retry: if the listing already holds the requested result, they succeed instead of reporting a stale page.
- Submit locks the listing row (`SELECT … FOR UPDATE`, the row created empty if missing) before reading it, so a review in flight waits and is then refused by its `seen` guard; nothing is overwritten from a stale read.
- A version sealed by a tooling submission and later reused by a hackathon submission keeps `SEAL_NOTE`, so the project page never labels it "replaced". Harmless; noted so nobody "fixes" `wasReplaced` for it.
- Pure rules in `_lib/rules.ts`, tested in `tests/tooling.test.ts`. Later: public project pages, showing the team.
