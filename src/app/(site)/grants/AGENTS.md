# Grants

Root AGENTS.md and CONTRIBUTING.md apply. This area reuses Hub projects, sessions, permissions, UI, audit and the shared project-submission rules. No internal JSON UI API, independent account system or duplicate project table.

- Public discovery is under `(site)/grants`; private applicant pages call `requireUser` and query current project membership. Readers may view; only current owner/writers may act. Staff routes call `requirePermission('grants.review')`. Nav mirrors that guard.
- Every exported server action is wrapped in `action`. Command writes re-read membership and effective capability, reject project-member self-review, and compare revisions in a serializable transaction. Missing object access throws `ForbiddenError`.
- Grant state is validated by `stateSchema`, stored as an aggregate plus an append-only `GrantRevision` receipt in the same transaction. Never accept a client state replacement or callback. The head revision is optimistic concurrency control. New schemas require a versioned state migration rather than silently changing stored state.
- Short Mini Grant intake uses `answers.intakeVersion: 2` in the existing aggregate. It records one whole-dollar request up to $10,000 and a dated deliverable with proposed evidence of completion. The applicant can choose a planned or in-progress milestone from the same project or enter an application-only milestone. The server rechecks the roadmap title, date and eligibility before submission. Application-only milestones do not write to the roadmap. Existing drafts and snapshots retain the original answer format.
- `GRANTS_SHORT_INTAKE_ENABLED` defaults off. With it off, new applications use the legacy form and existing v2 drafts are read-only. Both formats remain readable and submitted v2 cases can continue through review and award. Before enabling v2 writes, verify compatible readers and drain old instances. After the first v2 write, roll back only to a release that can still read v2 with the gate off.
- `GRANTS_MILESTONE_FIRST_ENABLED` defaults off and selects aggregate version 3 only at the first submission of an eligible short draft. Deploy and drain to version-3-compatible readers and writers before enabling it. Turning it off stops new enrollment and leaves existing version-3 cases operational. After the first v3 write, retain a version-3-compatible rollback artifact. Never down-convert a cleared or issued case.
- Version 3 uses the pinned submission through clearance (existing review and decision permissions), evidence from a project editor, verification (existing verify permission) and award issuance (existing decision, readiness and budget authority). Clearance alone authorizes neither award nor payment. Award issuance creates no applicant confirmation. Existing finance report/reconciliation and balance guards apply after an award. There is no public transaction link under the current finance data contract.
- Submission seals the existing current `ProjectVersion` atomically, using shared rules; later project edits do not rewrite application snapshots. Live `ProjectMilestone` is not agreed grant terms.
- Only staff with decision permission may release applicant-facing review statuses or reopen a deferred application. Reopening keeps the decision history and prompts a fresh assessment.
- Assessment, readiness, call priority, authorised award, confirmation, acceptance, payment and impact review are separate. The internal v2.0 template and 30/90/180-day monitoring remain proposed defaults until programme owners adopt them.
- Applicants receive an explicit server allowlist, never internal assessments/notes, authority/budget references, finance references or manual follow-ups. Short-intake award and amendment projections expose the released milestone, acceptance evidence, amount, date and maintainer. The server carries forward private award fields when the applicant proposes an amendment. Payment evidence is rendered only with `grants.payments`.
- USD uses integer cents. Payment records describe external finance activity; there is no transfer, wallet or provider integration. External references are unique across grants. Only confirmed records count as paid; reported/uncertain/disputed amounts reserve the obligation.
- Amendments are bounded to confirmed terms before acceptance/payment records. Renewed approval does not activate terms; applicant confirmation creates the next active version. Preserve prior versions and rejected/withdrawn proposals.
- Dates for deadlines are validated UTC calendar days, instants are server-generated UTC timestamps. Monitoring is anchored to accepted delivery. Blank observed metrics are unmeasured, not zero; measured values need evidence and method. Never sum cumulative checkpoint values or automatically rewrite c9.
- Reminder text is a draft only. No automatic send, external sync, award, XP or follow-on grant.
- Full round snapshots freeze every submitted member, source, hold and owner choice independently of client selection/filtering. They are read-only. Call choices cannot change scores, original intake categories or funding.
- Continuous Mini Grants use `GrantApplication.roundId = null` and start through `startApplication({ projectId })`. Legacy round drafts and cases keep their format and round submission rules. The `miniGrantsIntake` Hub flag defaults off. When on, it accepts roundless starts and submissions and disables legacy creation. When off, continuous drafts can be edited, submitted cases can proceed, and legacy creation again requires a published round.
- Roundless starts read project membership and same-project cases in the same serializable transaction as creation and the first revision. Retry serialization conflicts in a fresh transaction to resume the winning draft. Existing active cases and awards block a new case.
- The `miniGrantsReapplication` flag defaults off and requires continuous intake. The provisional fixture uses the latest native Mini Grants `not_selected` decision from an immutable decision receipt for the same Hub project, including native rounds. Start and submit both enforce 90 elapsed UTC days. Starting requires a different working-demo base URL or a different eligible roadmap deliverable. Submitting verifies the changed demo or the different eligible roadmap item with a changed deliverable and verification criterion against the prior pinned submission. Historical cases stay readable. Same-project awards and open cases block a new case. Grants Committee and Tech must confirm the fixture before activation.
- A continuous submission requires an HTTP(S) demo link on the pinned Hub project version. Saving a draft does not require proof. Server validation checks link format and presence. Reviewers inspect the actual demo.
- Apply the nullable-round migration and drain older instances before enabling the flag. After the first continuous write, retain a reader and writer that supports nullable-round cases as the rollback target.
- New continuous cases start in aggregate version 4 with `answers.intakeVersion: 3`. A draft can save zero to three items. Submission requires one to three complete, independently verifiable items and rechecks distinct roadmap selections in the project's live roadmap. The submitted application revision is the immutable plan and supplies server-assigned milestone IDs. Legacy drafts and submitted cases keep their own state and commands.
- Plan approval binds the sealed project version and submitted plan ID. Clarification replies leave both pinned. Evidence writes match the current case revision, approved plan, milestone and latest attempt. The first submission uses `previousAttemptId: null`; a resubmission identifies the returned attempt. Review targets the latest submitted attempt for that milestone. A return keeps other milestones' statuses and all prior attempts.
- Version 4 awards require all current-plan milestones to be verified, pinned scope, and existing readiness and decision authority. Applicant projections omit reviewer identity and internal verification details. Version 4 adds no SQL migration. Drain instances that cannot read version 4 before enabling continuous starts. Pausing intake leaves existing approved plans operational, and rollback requires version 4-capable readers and writers.
- Version 4 Hold and Decline use the authenticated decision actor. Hold records an applicant-facing reason and next step and keeps the active case. Decline keeps the immutable `record_decision` revision for reapplication. Staff reasons stay private. Rollback after these writes needs a reader that understands Committee decisions without approval references.
- Version 4 issuance needs server-sourced terms and Committee and Finance provenance bound to the case, exact revision, pinned plan and issuing actor. There is no live authority source yet. The public action supplies no authorization and the old reference-entry command cannot issue a v4 award. A successful issuance records its audit entry in the award transaction. Payment reporting and reconciliation still use the existing separate workflow.
